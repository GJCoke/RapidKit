# Redis-backed Worker Heartbeat Design

## Summary

Move Celery Worker liveness from periodic PostgreSQL updates to Redis keys with a 90-second TTL. PostgreSQL remains the system of record for Worker identity, capabilities, task counters, and the last confirmed status transition. Redis becomes the source of truth for the current heartbeat timestamp.

The existing Redis Stream continues to transport Worker lifecycle and heartbeat events. A normal heartbeat refreshes Redis without updating PostgreSQL. PostgreSQL is written only when a Worker is registered, changes between online and offline, or its persistent metadata changes.

This design preserves the existing Worker API shape, status filters, database pagination, and Socket.IO events. It requires no database migration and can be rolled back to the current implementation.

## Goals

- Eliminate the PostgreSQL `UPDATE worker_workers` transaction generated by every 30-second heartbeat.
- Detect an ungraceful Worker shutdown within 90 to 120 seconds.
- Detect recovery within one heartbeat interval, currently 30 seconds.
- Preserve the current Worker API response structure and status filtering behavior.
- Prevent Redis failures from falsely marking all Workers offline.
- Emit Socket.IO status events only when the effective status changes.

## Non-goals

- Replacing Redis Stream as the transport for task and Worker lifecycle events.
- Moving Worker registration, metadata, counters, or task history out of PostgreSQL.
- Deleting `status` or `last_heartbeat` from `worker_workers` in this change.
- Providing durable heartbeat history.

## Current Behavior

Each Celery Worker publishes `worker.heartbeat` to the `celery:events` Redis Stream every 30 seconds. The FastAPI consumer dispatches the event to `EventService.handle_worker_heartbeat()`, which queries the Worker by hostname and updates `last_heartbeat` and `update_time` in PostgreSQL. The session commits once the event has been handled.

An offline scanner queries online database rows whose persisted heartbeat is older than 90 seconds, marks them offline, resets their active-task count, and emits a status event.

At steady state, every Worker therefore causes one database query, update, and transaction every 30 seconds.

## Architecture

```text
Celery Worker
  |-- worker.online ---------> Redis Stream --+
  |-- worker.heartbeat ------> Redis Stream --+--> FastAPI consumer
  |-- worker.offline --------> Redis Stream --+       |
  |-- task.* ----------------> Redis Stream ---------+|
                                                       |
                         +-----------------------------+
                         |
                         |-- heartbeat TTL -----------> Redis
                         |-- identity/transitions ----> PostgreSQL
                         |-- status transitions ------> Socket.IO
```

### Responsibility split

PostgreSQL stores:

- Worker hostname and persistent identity.
- Concurrency, active queues, and software information.
- Processed-task and active-task counters.
- The last confirmed status transition.
- A persisted fallback value for `last_heartbeat`.

Redis stores:

- The real-time heartbeat timestamp.
- Worker liveness through key expiry.

Redis Stream transports:

- Worker online, heartbeat, and explicit offline events.
- Task started, succeeded, failed, retried, and revoked events.

## Redis Data Model

Each Worker has one key:

```text
rapidkit:worker:heartbeat:<hostname>
```

The value is the consumer's current naive UTC time formatted as ISO 8601. The first version deliberately uses consumption time rather than event time so delayed or out-of-order timestamps cannot shorten or incorrectly extend liveness.

The key is written atomically with a TTL:

```text
SET rapidkit:worker:heartbeat:<hostname> <utc-iso-timestamp> EX 90
```

Constants are defined in one heartbeat-store module:

```python
HEARTBEAT_KEY_PREFIX = "rapidkit:worker:heartbeat:"
HEARTBEAT_TTL_SECONDS = 90
```

Hostnames are preserved verbatim and key construction is centralized. No code scans Redis by key pattern during normal operation.

Redis data loss is acceptable. After a Redis restart, an active Worker recreates its key on its next heartbeat, within approximately 30 seconds.

## Components

### `WorkerHeartbeatStore`

Add `apps/backend/plugins/worker/src/plugin_worker/heartbeat_store.py`. This component owns Redis key construction, serialization, pipeline access, and error classification.

It exposes:

```python
class WorkerHeartbeatStore:
    async def touch(self, hostname: str) -> datetime: ...
    async def remove(self, hostname: str) -> None: ...
    async def get(self, hostname: str) -> datetime | None: ...
    async def get_many(self, hostnames: list[str]) -> HeartbeatBatchResult: ...
    async def find_missing(self, hostnames: list[str]) -> HeartbeatBatchResult: ...
```

`HeartbeatBatchResult` distinguishes a successful lookup containing missing keys from a Redis lookup failure. Callers must never interpret a Redis failure as every Worker being offline.

`get_many()` and `find_missing()` use a Redis pipeline. Empty input returns immediately without contacting Redis.

### `EventService`

Inject `WorkerHeartbeatStore` into `EventService`; the service must not obtain a global Redis client internally.

`handle_worker_heartbeat()` performs these actions:

1. Validate and normalize the hostname.
2. Refresh its Redis heartbeat key.
3. Query the database Worker by hostname.
4. If the Worker does not exist, log a warning and stop.
5. If the persisted status is already online, make no ORM mutation and emit no Socket.IO event.
6. If the persisted status is offline, set it online, persist the transition timestamp in `last_heartbeat` and `update_time`, flush once, and emit one status event.

The consumer acknowledges a heartbeat event even when Redis is unavailable. Retrying such events through the Stream would delay unrelated lifecycle and task events and would not create durable liveness. The Worker will publish another heartbeat after 30 seconds.

`handle_worker_online()` upserts persistent metadata, sets the database status online, initializes the Redis heartbeat key, persists the transition heartbeat, and emits an online event.

`handle_worker_offline()` removes the Redis key. It updates PostgreSQL, resets `active_task_count`, and emits an event only if the effective database status was not already offline. Repeated offline events are idempotent.

### `WorkerCRUD`

Replace the time-based `get_offline_workers()` query with `get_online_workers()`. CRUD remains responsible only for PostgreSQL access and must not read Redis.

Database `status` remains a materialized, queryable representation of the last confirmed status. This preserves database pagination and `status=online|offline` filters.

### `WorkerService`

Add `apps/backend/plugins/worker/src/plugin_worker/worker_service.py` to compose Worker database results with real-time Redis heartbeat data.

It exposes paginated, complete-list, and detail reads. For a list response, it retrieves database rows normally and uses one Redis pipeline for the returned hostnames. A successful Redis value replaces the response's `lastHeartbeat`; an expired key retains the persisted fallback value while `status` follows the database transition state.

If Redis cannot be read, the service returns the database result unchanged. API availability does not depend on real-time heartbeat enrichment.

Worker list/detail endpoints use an injected `WorkerService`. Control endpoints that require ORM entities continue to use `WorkerCRUD` directly.

## Event Flows

### Normal heartbeat

1. Worker publishes `worker.heartbeat` every 30 seconds.
2. Consumer refreshes the 90-second Redis key.
3. Consumer queries the persistent Worker.
4. If already online, it acknowledges the event without a database update or WebSocket emission.

### Initial online event

1. Worker publishes `worker.online` when ready.
2. Consumer upserts the Worker metadata and online status.
3. Consumer initializes the Redis key.
4. Consumer persists `last_heartbeat` for the transition.
5. Consumer emits one online status event.

### Explicit shutdown

1. Worker publishes `worker.offline` during graceful shutdown.
2. Consumer deletes the heartbeat key.
3. Consumer transitions the database status to offline and resets active tasks.
4. Consumer emits one offline status event.

### Ungraceful shutdown

1. Heartbeats stop and the Redis key expires after 90 seconds.
2. The leader FastAPI instance runs the offline scan at its existing 30-second interval.
3. It loads database Workers whose status is online.
4. It checks all corresponding keys in one Redis pipeline.
5. On a successful Redis result, it rechecks each missing key before changing the Worker. This closes the race with a heartbeat arriving during the scan.
6. Confirmed missing Workers are transitioned to offline, their active-task counts are reset, and one event per transition is emitted.
7. All transitions are flushed together and committed by the session lifecycle.

The maximum expected detection time is approximately TTL plus one scan interval: 120 seconds.

### Recovery after timeout or Redis restart

1. A new heartbeat recreates the Redis key.
2. If PostgreSQL still says online, no database write is needed.
3. If an offline scan already changed the database status, the heartbeat transitions it to online and emits one recovery event.

## Consistency and Concurrency

- The Redis key is the real-time source for `lastHeartbeat`; PostgreSQL `status` is the queryable transition state.
- Only a confirmed state transition writes PostgreSQL.
- Only the existing leader-elected background process performs offline scanning.
- Before marking an apparently missing Worker offline, the scanner performs a second key check to avoid racing a new heartbeat.
- Online and offline handlers are idempotent and emit only on effective state changes.
- A restarted Worker with the same hostname reuses and refreshes its existing database record.
- Task lifecycle events continue to update task counters in PostgreSQL; these writes are not heartbeat writes and remain unchanged.

There can be a bounded interval between Redis key expiry and the next offline scan during which the database status still reads online. This is accepted and is limited to about 30 seconds after expiry.

## Failure Handling

### Redis write failure

- Log a warning without credentials or sensitive configuration.
- For `worker.heartbeat`, do not mutate the database heartbeat or status based on an unrecorded heartbeat.
- For explicit `worker.online` and `worker.offline` lifecycle events, continue persisting the lifecycle transition; Redis will be repaired by a later heartbeat or key removal.
- Acknowledge the Stream event so task and lifecycle processing is not blocked.
- Allow the next Worker heartbeat to repair the state.

### Redis batch-read failure

- Worker API reads fall back to persisted response values.
- Offline scanning skips the entire cycle.
- No Worker is marked offline.

### Unknown Worker heartbeat

- Refresh the Redis key first so a slightly delayed online event does not cause a false timeout.
- Log a warning for diagnostic visibility.
- Do not create a partial database Worker from heartbeat data; registration remains the responsibility of `worker.online`.

### PostgreSQL failure

- Existing session rollback behavior remains authoritative.
- A successfully refreshed Redis heartbeat may temporarily coexist with stale database status. A later heartbeat or scan reconciles the status.

## Logging

- Successful steady-state heartbeat refreshes produce no INFO log.
- Worker online and offline transitions use INFO.
- Unknown Worker heartbeats and Redis failures use WARNING.
- Redis read failures during offline scans include enough context to identify the skipped scan but never include Redis credentials.
- SQLAlchemy engine logging is configured independently; this feature does not depend on suppressing SQL logs.

## API Compatibility

No endpoint or response-schema change is required:

```http
GET /workers
GET /workers/all
GET /workers/{worker_id}
```

Existing `status=online|offline` filters and database pagination remain valid because PostgreSQL retains the transition status. `lastHeartbeat` becomes fresher when Redis is available and falls back to its persisted transition value otherwise.

## Testing

### Heartbeat store unit tests

- `touch()` stores the expected value and a 90-second TTL.
- Repeated `touch()` renews the TTL.
- `remove()` is idempotent.
- `get()` distinguishes an expired key from a valid value.
- `get_many()` pipelines reads and maps values to hostnames.
- Batch results distinguish missing keys from Redis failure.
- Empty batch operations do not call Redis.

### Event service unit tests

- A heartbeat for an online Worker refreshes Redis without mutating the ORM Worker or flushing.
- A heartbeat for an offline Worker performs one transition and emits one status event.
- Repeated heartbeats after recovery do not emit duplicate events.
- Online registration writes persistent metadata and initializes Redis.
- Explicit offline removes Redis state and performs one idempotent transition.
- An unknown hostname logs a warning without creating a Worker.
- Redis failure does not create a false online transition.

### Offline scanner tests

- Only online Workers with missing heartbeat keys are marked offline.
- Existing keys leave Workers unchanged.
- A key recreated before the confirmation check prevents an offline transition.
- Redis batch failure skips the scan without database mutations.
- Multiple expired Workers are flushed as one batch.
- Only the leader executes the scanner.

### Query service tests

- Redis timestamps enrich list, all-list, and detail responses.
- Pipeline access prevents per-row Redis calls.
- Redis failure returns persisted values.
- Existing pagination totals and status filters are unchanged.

### Integration tests

- A started Worker becomes online within 30 seconds.
- An ungracefully stopped Worker becomes offline within 120 seconds.
- After Redis restarts, an active Worker recovers within 30 seconds.
- One stopped Worker does not affect another Worker.
- Stable heartbeats execute no `UPDATE worker_workers` statement.
- Status transitions produce one Socket.IO event each.

## Rollout and Rollback

1. Deploy the new code while retaining the existing database columns.
2. Heartbeat processing immediately starts writing Redis and stops steady-state heartbeat updates in PostgreSQL.
3. Wait at least 90 seconds after all application instances are upgraded so active Workers establish heartbeat keys.
4. Enable the Redis-based offline scanner as part of the same release only after this warm-up. This can be implemented with a startup grace period of 90 seconds, avoiding a separate deployment toggle.
5. Verify Worker list enrichment, status filters, Socket.IO transitions, Redis key TTLs, and absence of steady-state heartbeat updates.
6. Observe for at least one normal release cycle before considering removal of the database fallback column. This design recommends retaining it.

Rollback requires only redeploying the prior version. The existing columns remain intact, and the next heartbeat resumes periodic database updates. Redis heartbeat keys can expire naturally and need no cleanup.

## Acceptance Criteria

- A steady-state heartbeat performs no PostgreSQL `UPDATE` on `worker_workers`.
- An ungracefully stopped Worker is displayed offline within 120 seconds.
- A recovered Worker is displayed online within 30 seconds.
- Redis read failure cannot trigger mass offline transitions.
- Online and offline transitions produce exactly one Socket.IO event.
- Existing Worker API contracts, status filters, and pagination remain compatible.
- No database migration is introduced.

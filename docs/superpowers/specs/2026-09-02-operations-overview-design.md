# 运营总览改造设计

## 目标

改造 `apps/frontend` 首页，在首屏提供统一的运营总览，使运营和管理员能够快速判断：服务是否健康、活跃用户是否变化、任务量是否变化、API 是否稳定，以及系统近期趋势和关键运行状态。

本次改造以现有首页为基础，不新增独立菜单。运营总览替换首页中重复的统计卡和趋势卡；活动动态、业务数据、基础设施和 API 详情等现有模块继续保留在其下方。

## 页面结构

运营总览使用一张完整卡片，由一个卡片头部和三层内容组成：

1. 顶部包含“运营总览”标题和时间范围选择器。默认选择近 7 天，支持近 7 天、近 30 天和自定义范围。
2. 第一层展示服务状态、活跃用户、今日任务、API 错误率四项核心指标。
3. 第二层展示趋势图，通过分段选择器在“请求次数”和“平均响应时间”之间切换。
4. 第三层展示系统运行时间、队列深度、最后数据同步、过去 7 天任务成功率。

桌面端四项指标横向排列，并通过分隔线形成清晰的信息组。窄屏下改为两列或单列。趋势图必须保留可读坐标和悬浮提示，不通过过度压缩适配移动端。

页面沿用 RapidKit 的主题变量、圆角、暗色模式、响应式规则和首页权限机制。视觉密度参考用户提供的示例，但不复制固定白底或与现有设计系统冲突的样式。

## 指标口径

所有日级统计按 `Asia/Shanghai` 自然日划分。聚合响应同时返回生成时间和时区，避免前后端自行推断统计边界。

### 服务状态

- 总数是已注册且应参与运行的 Worker/服务器实例数。
- 正常数是最近一次心跳仍在有效期内的实例数。
- 任一实例离线、心跳超时或不可用时，整体状态为 `degraded`；全部不可用时为 `down`。
- PostgreSQL、Redis、MinIO 等基础设施不计入服务器数量。
- 展示格式为“正常数 / 总数”，例如 `2 / 2` 或 `1 / 2`。

### 活跃用户

- 活跃用户是自然日内产生有效会话或业务访问的去重用户数。
- 同一用户一天内多次访问只计一次。
- 变化率为 `(今日 - 昨日) / 昨日 × 100%`。
- 昨日为 0 时变化率返回 `null` 并展示“—”；今日和昨日均为 0 时返回 `0%`。

### 执行任务

- 任务按实际开始执行时间归入对应自然日。
- 包含成功、失败、重试中、运行中和已撤销任务。
- 仅创建但尚未被 Worker 接收的任务不计入执行数。
- 变化率计算和零值规则与活跃用户一致。

### API 错误率

- 错误率为 `(HTTP 5xx 数量 + 明确定义为失败的业务异常数量) / API 请求总数 × 100%`。
- 今日和昨日独立计算。
- 对比值使用百分点：`今日错误率 - 昨日错误率`。
- 错误率下降显示绿色，上升显示红色。
- 当请求总数为 0 时，错误率及其变化返回 `null` 并展示“—”。

### 请求与响应趋势

- 请求次数是每日 API 请求总量。
- 响应时间是每日按请求数加权的平均响应时间，单位为毫秒，不与 P95 混用。
- 默认返回最近 7 个自然日；当天数据为截至响应生成时的累计值。
- 请求次数使用整数纵轴，响应时间使用毫秒纵轴，悬浮提示同步展示日期、数值和单位。

### 系统运行状态

- 系统运行时间从当前后端主实例最近一次启动时间计算，多实例部署时明确标注为主实例运行时间。
- 队列深度是当前等待执行的任务数，不包含运行中的任务；对比值采用昨日同一时刻的快照。
- 最后数据同步是监控聚合数据最近一次成功写入时间。超过阈值时显示 `delayed`，明确失败时显示 `failed`。
- 过去 7 天任务成功率为成功终态任务数除以全部终态任务数；等待中、运行中和重试中任务不进入分母。
- 过去 7 天任务成功率与前一个完整 7 天周期比较，变化值使用百分点。

## API 设计

新增聚合接口：

`GET /api/v1/dashboard/operations-overview?range=7d`

`range` 首期支持 `7d`、`30d` 和自定义起止时间。接口返回一个时间点一致的运营快照，避免前端调用多个接口后产生跨统计边界的不一致。

```ts
interface OperationsOverview {
  generatedAt: string
  timezone: "Asia/Shanghai"
  summary: {
    servers: {
      healthy: number
      total: number
      status: "healthy" | "degraded" | "down"
    }
    activeUsers: {
      today: number
      yesterday: number
      changePercent: number | null
    }
    tasks: {
      today: number
      yesterday: number
      changePercent: number | null
    }
    apiErrorRate: {
      today: number | null
      yesterday: number | null
      changePoints: number | null
    }
  }
  trend: Array<{
    date: string
    requestCount: number
    avgResponseMs: number | null
  }>
  system: {
    startedAt: string
    uptimeSeconds: number
    queueDepth: number
    queueDepthYesterday: number | null
    queueDepthChangePercent: number | null
    lastSyncAt: string | null
    syncStatus: "healthy" | "delayed" | "failed"
    taskSuccessRate7d: number | null
    previousTaskSuccessRate7d: number | null
    taskSuccessRateChangePoints: number | null
  }
}
```

接口受现有首页权限控制。对应首页模块键继续使用 `dashboard.overview`，并在插件能力清单中注册聚合接口权限。

## 现有能力与缺口

可复用能力：

- Worker 注册、状态与心跳数据可作为服务状态基础。
- 任务结果表和现有任务汇总、时间线查询可作为任务统计基础。
- `monitoring_api_metrics_hourly` 已保存请求数、错误数和平均响应时间，可生成错误率及趋势。
- 现有首页具备模块权限、并行加载、Socket.IO 更新、ECharts、国际化和响应式布局基础。

需要补充的服务端能力：

- 当前用户统计主要覆盖用户总数、新增用户和在线数，缺少按自然日去重的活跃用户事实数据。
- 当前任务 `days=1` 使用滚动 24 小时窗口，不能准确表达今日与昨日自然日。
- 当前错误统计接口主要是近 1 小时数据，不能提供今日、昨日的独立错误率。
- API 趋势已有请求量与平均响应时间基础，但需要按自然日聚合并补齐没有数据的日期。
- 缺少稳定的应用启动时间输出。
- 缺少当前队列深度的历史快照，因此无法比较昨日同一时刻。
- 缺少监控数据最后成功同步时间和同步健康状态。
- 当前任务成功率使用全部记录作为分母，需要增加仅基于终态任务的 7 日周期计算。

## 数据存储与采集

新增用户日活事实表，以日期和用户 ID 建立唯一约束。有效鉴权后的业务访问通过低开销、可幂等的方式写入；健康检查、静态资源、登录失败和系统内部请求不计入日活。

新增系统指标快照表，至少保存采样时间、队列深度和同步状态。采样频率应足以支持“昨日同一时刻”比较，同时设置合理保留期，避免无限增长。昨日对比选择最接近目标时刻且在允许误差窗口内的快照；不存在匹配快照时返回 `null`。

应用启动时间保存在当前进程生命周期状态中。若主实例发生切换，新主实例的启动时间成为总览基准。

历史数据不存在时不回填虚构值。页面统一用“—”表示不可获得的历史对比，并保持当前值可用。

## 前端设计

新增 `operations-overview.vue`，组件只负责展示和交互。数据获取、范围选择、加载状态和刷新放在 `use-dashboard` 中，接口定义放在现有 service 与 typings 层。

运营总览替换当前 `stat-cards.vue` 与首页主趋势区域。现有活动动态、业务数据、基础设施、应用健康与 API 详情继续保留。若应用健康卡与新总览产生明显重复，只在后续实现计划中做局部字段重排，不删除更细粒度的 P50、P95、WebSocket 等诊断信息。

每个指标支持独立不可用状态。聚合接口应尽量返回可用的部分；前端不会因为一个来源失败而把整张卡替换为空状态。整次请求失败时显示卡片级错误和重试入口。

数值使用等宽数字排版。`null` 与真实的 `0` 必须区分。变化指标同时使用箭头、正负号和文字/颜色表达，不能只依赖颜色传递含义。

## 实施阶段

1. 后端统计基础
   - 统一自然日和时区边界工具。
   - 增加用户日活采集与去重存储。
   - 增加队列深度和同步状态快照。
   - 暴露应用启动时间。
   - 固化 Worker 心跳健康判定。
2. 后端聚合接口
   - 新增响应模型和聚合服务。
   - 实现今日/昨日用户、任务、错误率统计。
   - 实现请求次数和平均响应时间趋势。
   - 实现当前及历史队列深度、同步状态和两段 7 日任务成功率。
   - 注册路由、权限和首页模块能力。
3. 数据库迁移
   - 创建用户日活表、系统指标快照表和必要索引。
   - 提供可逆升级/降级脚本。
4. 前端数据层
   - 更新 OpenAPI schema、类型和请求函数。
   - 扩展 `use-dashboard`，默认范围设为 `7d`。
   - 管理局部数据不可用和整体请求失败状态。
5. 前端界面
   - 实现运营总览组件、指标区、趋势切换和底部状态区。
   - 替换重复的统计卡与趋势卡。
   - 补齐中英文文案、暗色模式和响应式行为。
6. 验证
   - 执行后端单元与接口测试、前端类型检查和构建。
   - 验证桌面、平板、手机及暗色模式。
   - 对照参考图检查信息层级、数字对齐、留白和图表可读性。

## 测试与验收

后端覆盖服务 `2/2`、`1/2`、`0/2`、无注册实例及心跳边界；覆盖日活去重和跨日；覆盖任务日期归属与状态；覆盖错误率、零请求和百分点变化；覆盖 7 日终态任务成功率；覆盖队列快照匹配、单一数据源失败和接口权限。

前端覆盖涨跌方向、颜色、单位和空值；覆盖服务异常；覆盖请求次数与响应时间切换；覆盖默认近 7 天；覆盖局部失败、亮暗主题、中英文和响应式布局；验证原有首页模块权限过滤仍然有效。

验收标准：用户进入首页后，无需滚动即可看到四项核心指标、默认近 7 天趋势和四项系统运行状态；各指标符合本文口径，异常和缺失数据有明确表现，且不会把缺失历史数据显示为零。

## 非目标

- 本次不新增独立运营总览菜单或页面。
- 本次不移除现有的活动、业务、基础设施和 API 诊断详情。
- 本次不提供任意指标自由组合、拖拽布局或用户自定义仪表盘。
- 本次不伪造或估算上线前不存在的历史快照数据。

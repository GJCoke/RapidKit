# Repository Instructions

## Git workflow

- Classify every new task first. A **simple task** meets all of these: it needs no design document or plan; it touches at most 1–2 files and a few dozen lines; it has no database migration and changes no API contract or permission declaration. Typical simple tasks: a typo, copy text, a single configuration value, a docs-only edit, an obvious one-line bug fix. When in doubt, treat the task as non-simple.
- A simple task may be done directly on the current branch in the current checkout, without a worktree or a new branch.
- Every non-simple task gets a new worktree with a freshly created branch before any repository file is edited, including design documents and plans. Inspect the current branch and working tree, record the entry branch, then run `git worktree add -b <type>/<slug> .worktrees/<type>-<slug> HEAD` and do all further work inside that worktree. Verify the worktree is on the new branch.
- Branch names are `<type>/<slug>`. `<type>` is one of `feature`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`; `<slug>` is lowercase English kebab-case naming the concrete change, e.g. `feature/login`, `fix/login-cooldown`, `refactor/permission-grants`. Do not use the `codex/` prefix for new branches.
- The worktree starts from HEAD, so uncommitted changes in the main checkout are not carried over; they stay untouched where they are. Install the dependencies the task needs inside the new worktree (`pnpm install` for frontend work, `uv sync` for backend work) before running checks.
- Continue in the same worktree and branch for clarifications, validation retries and follow-up fixes within that task; do not create another worktree or branch for each skill invocation or message. A separate new task requires a fresh worktree and branch.
- Preserve all pre-existing staged, unstaged and untracked changes. Do not reset, clean, stash or discard them. If worktree or branch creation is blocked, stop before editing and report the blocker; do not fall back to the entry branch or detached HEAD.
- Files under `docs/superpowers/` written in a worktree exist only there. Before a worktree is removed, remind the user and let them choose whether to copy those files back to the main checkout or discard them.
- After the required validation passes, task implementation files (source code, tests, configuration and maintained skill instructions) may be committed automatically. Stage explicit task-owned paths or hunks and review the staged diff first. If task changes cannot be separated safely from pre-existing work, leave them uncommitted and report that fact.
- Never stage or commit task design documents, specifications or implementation plans, regardless of their location or extension. Everything under `docs/superpowers/` (specs, plans and any other file there) stays local and uncommitted; do not force-add ignored planning artifacts.
- Never use blanket staging (`git add .`, `git add -A`) or `git commit -a`. Before committing, check the staged file list and diff, exclude design/plan artifacts, and ensure no unrelated pre-existing changes are included.
- Permission to create a branch or commit implementation does not authorize pushing, merging, rebasing, amending history or deleting branches; perform those actions only when the user explicitly requests them. Removing a worktree also needs the user's explicit choice.
- These repository rules take precedence over Git steps in generic workflow skills. In this repository, workflow instructions to commit a spec/plan, implement a non-simple task on its entry branch, bypass worktree/branch setup, or use a different branch naming scheme must not be followed.
